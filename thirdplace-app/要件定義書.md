# THE THIRDPLACE EBISU 出欠管理システム 要件定義書

version 1.0 / 2026年8月

---

## 1. 背景・目的

THE THIRDPLACE EBISUでは、夜ラン・朝ラン・フットサル・軽井沢ツアーなど複数のイベントを、定例（毎週・毎月）／単発／不定期という異なるパターンで開催している。

これまでClaude Artifacts上でHTMLツールを作成し、Google Apps Script + スプレッドシートでの出欠管理を試みたが、以下の課題が発生した。

- Claude Artifactsのプレビュー経由だと、LINE内蔵ブラウザ等でキャッシュが残り最新情報が反映されない
- Google Apps Scriptのデプロイ管理が煩雑（バージョン反映漏れ、認証確認画面、CORS等）
- 継続的な運用・更新をチーム（伊藤・川島・酒井）で行うには属人的すぎる

このため、**独立したWebアプリケーションとして開発し、安定したURLで運用できる状態**を目指す。本書はその開発のための要件定義書である。

---

## 2. 想定ユーザー

| ユーザー種別 | 説明 | 主な操作 |
| --- | --- | --- |
| 参加者 | コミュニティメンバー・イベント参加希望者 | イベント閲覧、出欠回答、キャンセル・変更 |
| 幹事 | 伊藤・川島・酒井、運営スタッフ | イベント作成・編集、出欠状況の確認、過去履歴の閲覧 |

現時点では幹事側にログイン・認証機能はなく、タブ切り替えのみで区別している（要検討事項に後述）。

## 3. 機能要件

### 3.1 イベント管理

- イベントには以下の開催パターンを設定できる
  - **毎週定例**（例：毎週月曜20:00〜）
  - **毎月定例**（例：毎月第3月曜19:00〜）
  - **単発**（日付を直接指定。例：9/21開催のフットサル）
  - **不定期**（曜日固定なし、都度日程を決めて更新。例：フットサル初期状態）
- 毎週／毎月定例の場合、**次回開催日を自動計算**して表示する
- イベントごとに以下の項目を保持する
  - タイトル、絵文字アイコン
  - 開催場所
  - 詳細説明文（複数行）
  - 定員（任意、未設定なら無制限）
  - 締切（開催日の何日前か。任意）

### 3.2 参加者：出欠回答

- イベント一覧から回答したいイベントを選択
- 「① イベントを選ぶ → ② お名前を入力 → ③ 出欠を選んで送信」の3ステップで完結
- 出欠は「参加／未定／不参加」の3択
- 同じ名前で再送信すると、内容が上書き編集される（同一人物の回答として扱う）
- 定員に達している場合、「参加」の新規回答を受け付けない（自動締切）
- 締切日を過ぎている場合、回答フォーム自体を非表示にし「募集を締め切りました」と表示
- 定例イベントの場合、出欠データは「イベント×開催日」単位で管理し、開催日が変わるごとに新しい回答としてリセットされる

### 3.3 幹事：集計・履歴管理

- 各イベントの現在の回答状況をリアルタイムで確認できる
  - 参加／未定／不参加のそれぞれの人数
  - 回答者の名前と回答内容の一覧
- 過去に開催された回（today以前の日付）の履歴を、日付ごとの集計サマリーで閲覧できる

### 3.4 外部リンク導線

- 各イベントカードから Instagram（@the.thirdplace.ebisu）へのリンク
- ページ上部バナーからLINEオープンチャットへの参加導線
- 「予約・出欠はこのページ、日々の発信はLINEオープンチャット」という役割分担を明示

### 3.5 通知・連携（現状スコープ外／将来検討）

- 参加者の回答をLINEやメールへ自動通知する機能は**現状なし**
- 必要であれば将来的に検討（Webhook経由でのLINE通知等）

## 4. 非機能要件

### 4.1 デザイン

- ブランドトーン：深緑（#0c1815系）をベースに、ゴールド（#D9B876系）とオフホワイト（#FBF9F2）を組み合わせたラグジュアリー路線
- 書体：見出しにNoto Serif JP／Cormorant Garamond、本文にNoto Sans JP
- モバイル最優先（LINEやInstagramから開かれる前提のレスポンシブ対応）

### 4.2 可用性・パフォーマンス

- URLは固定・安定しており、更新のたびにリンクを送り直す必要がないこと
- ブラウザキャッシュにより情報が古くなる問題が起きないこと（キャッシュ制御ヘッダーの適切な設定）
- LINEアプリ内蔵ブラウザでも問題なく表示・動作すること

### 4.3 データ永続性

- 出欠回答データは永続的に保存され、消失しないこと
- 過去の開催履歴も参照可能な形で保持すること

## 5. データ構造（案）

### イベント（events）

| フィールド | 型 | 説明 |
| --- | --- | --- |
| id | string | イベント識別子 |
| title | string | イベント名 |
| emoji | string | アイコン |
| location | string | 開催場所 |
| description | text | 詳細説明 |
| recurrence_mode | enum | weekly / monthly / once |
| weekday | int | 曜日（0-6） |
| nth | int | 第n週（monthlyのみ） |
| time | string | 開始時刻 |
| date_iso | datetime | 単発開催日（onceのみ） |
| capacity | int (nullable) | 定員 |
| deadline_days_before | int (nullable) | 締切（開催日の何日前） |

### 出欠回答（responses）

| フィールド | 型 | 説明 |
| --- | --- | --- |
| event_id | string | 対象イベントID |
| occurrence_date | date | 対象の開催日（単発の場合は固定値） |
| name | string | 回答者名 |
| status | enum | go / maybe / no |
| updated_at | datetime | 回答日時 |

## 7. 技術スタック（検討中・要相談）

現状はClaude Artifacts上の単一HTMLファイル（バニラJS）＋Google Apps Script／スプレッドシートで検証してきたが、本格運用にあたっては以下のような構成を検討する。

| 候補 | メリット | 留意点 |
| --- | --- | --- |
| Next.js + Vercel + Supabase（or Firebase） | 安定したホスティング、DB永続化、認証機能も拡張しやすい | 開発・運用にエンジニアリングの継続的な関与が必要 |
| Google Apps Script + スプレッドシート継続 | 追加コストなし、非エンジニアでも中身が見える | デプロイ管理が煩雑、スケールに弱い、今回発生した問題が残る |
| ノーコードツール（Glide, Softr等） | 開発スピードが早い | 月額コスト、カスタマイズの自由度に制限 |

→ 方向性については、実際にコードで開発を進める前提であれば **Next.js + Vercel + Supabase** 構成を軸に、Claude Codeで実装を進めるのが現実的と思われる。

## 8. 今回の検証で得られた学び（引き継ぎ事項）

- CSSのIDセレクタに`:`（コロン）を含めると壊れる（イベントID+日付の組み合わせキーを使う際は要注意）
- Claude Artifactsのプレビューはキャッシュが残りやすく、本番運用のリンクとしては不向き
- Google Apps Scriptは「コード保存」と「デプロイへの反映」が別操作であり、更新の都度「デプロイを管理」から新しいバージョンを選択する必要がある
- 定例イベントは「イベントID × 開催日」で回答データを管理する設計が有効（開催日ごとに自動リセットされる）
